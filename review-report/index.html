🔴 严重级别 Bug（可能影响功能/安全）

B-01: EventStateStore 文件持续增长无上限
严重   state.py:28-37   |   内存 + 磁盘

seen_events.jsonl 只追加不清理，长期运行后文件无限增长。每次启动全量加载到内存 _seen: set[str]，大量事件后 OOM 风险。

修复：添加按时间窗口的事件淘汰机制（如保留最近24h或最近10000条），启动时只加载近期记录。或改用 SQLite + TTL 索引。
B-02: agents.py 超大单文件 — God Object 反模式
严重   agents.py (9,671行)   |   可维护性

agents.py 承载了 Claude/Codex/Bug/Perception/omlx 全部 Agent 编排逻辑，包括日志解压、文件分类、脚本执行、HTML 合并、Agent 增强总结等。混合了 IO 操作、业务逻辑和模板代码。

修复：拆分为 agents/claude_runner.py、agents/bug_runner.py、agents/omlx_client.py、agents/perception_runner.py、agents/log_processor.py 等独立模块。
B-03: setattr(self.bug_runner, "_lark_client", ...) 隐式注入
严重   app.py:283   |   设计缺陷

BridgeApp.__init__ 通过 setattr 向 BugAnalysisRunner 注入 _lark_client，绕过了 dataclass(slots=True) 的类型安全。这是典型的猴子补丁，代码阅读者无法从类定义发现该依赖。

修复：将 lark_client 作为 BugAnalysisRunner.__init__ 的显式参数，或在 Runner 构造时注入。
B-04: HTTP 报告服务绑定 0.0.0.0 且无鉴权
严重   config.example.toml:129 + report_server.py   |   安全

默认配置 bind_host = "0.0.0.0"，使 HTTP 服务暴露在局域网所有接口。报告服务和 Admin API 没有任何认证，任何同网段用户可访问 /api/sessions、/api/cases、删除分析历史等。

修复：默认绑定 127.0.0.1（代码中已是默认值，但配置示例写 0.0.0.0 会误导），管理 API 添加 Bearer Token 或 Basic Auth。

🟠 重要级别 Bug（影响可靠性/性能）

B-05: ConversationContextStore 全量 JSON 序列化无并发保护
重要   state.py   |   数据一致性

每次保存都是全量写入 conversation_contexts.json。虽然有 threading.Lock，但如果在写入过程中进程崩溃，JSON 可能损坏。多个并发事件处理时，高频的全量序列化也影响性能。

修复：采用 write-then-rename 的原子写入模式，或改用 SQLite WAL 模式。
B-06: _download_url 未校验重定向目标
重要   downloader.py:48-78   |   安全 (SSRF)

urllib.request.urlopen 会自动跟随 HTTP 重定向。攻击者可以在飞书消息中构造外部 URL 重定向到内网地址（如 http://169.254.169.254），形成 SSRF。

修复：使用自定义 HTTPRedirectHandler 限制重定向目标为公网地址，或禁止重定向并返回最终 URL 让用户确认。
B-07: 进度卡片 _progress_cards 内存字典无清理上限
重要   app.py:254   |   内存泄漏

_progress_cards: dict[str, dict] 在事件处理中持续添加条目，仅在卡片成功完成后清理。如果 _finish_progress_card 失败（网络问题等），条目会永远留在内存中。

修复：为 _progress_cards 设置 TTL 清理机制（如 2h 自动过期），或使用 collections.OrderedDict + 容量上限。
B-08: _optional_path 错误消息硬编码为 "claude_agent.working_dir"
重要   config.py:317   |   代码质量

_optional_path 被多个配置项复用（bug_analysis.working_dir, intent_analysis.working_dir 等），但报错消息始终为 "claude_agent.working_dir must be a path string"。

修复：添加 field_name 参数传入实际字段名。
B-09: app.py 路由优先级耦合过紧
重要   app.py:392-604   |   可维护性

_handle_event 方法超过 200 行 if-elif-else 串联判断，每种请求类型的判断顺序隐含了优先级语义但无文档说明。新增路由需要小心地插入到正确位置。

修复：将路由逻辑抽象为有序的 RouteHandler 链，每个处理器自行判断 can_handle() + handle()，支持优先级配置。
B-10: omlx_chat API 密钥可能以空字符串形式提交
重要   agents.py:247-270   |   安全

当 api_key 为空字符串时，HTTP 请求仍然会发送 Authorization: Bearer （空值），部分 API 实现可能会因此返回 500 而非 401。

修复：在 _chat 方法中，api_key 为空时跳过 Authorization header 或提前报错提示配置缺失。

建议：引入 logging 模块，使用分层 logger（bridge.app, bridge.agents 等），支持 JSON 格式输出。

两个集合大部分内容相同，维护时容易不一致。

建议：合并为一个集合，域特定扩展通过 set.union() 实现。
B-14: 多处 [:500] / [:300] 截断缺少一致性
建议   多文件   |   一致性

错误消息截断使用不同的魔法数字（500, 300, 700），应抽取为常量。

建议：定义 MAX_ERROR_PREVIEW_CHARS = 500 等常量并统一使用。
B-15: 测试覆盖率未量化，无集成测试
建议   tests/   |   质量保障

414 个单元测试全部通过，但缺少覆盖率度量和端到端集成测试（如模拟完整事件→报告发布流程）。

建议：引入 coverage 工具，目标覆盖率 ≥80%。添加关键路径的 integration test。

WebUI 现状评估

当前 Admin UI 分析

后台管理界面以 admin_ui.py 中 681 行内联 HTML/CSS/JS 实现，是一个功能完整的 SPA。支持 4 个 Tab 页面：多会话进度、分析历史、Skill 管理、运行状态。

✅ 做得好的地方

  • 零外部依赖的纯 HTML/CSS/JS 实现，符合项目"仅标准库"的理念
  • 全局实时刷新 (5s 轮询)，支持 URL 参数定位会话
  • 功能完整：进度条、时间线、Skill CRUD、调试面板、分析历史搜索过滤
  • 响应式设计（有移动端断点适配）

❌ 需要改进的地方

  • 视觉层次不清：所有 Tab 内容结构和视觉权重一致，缺少信息层次梯度
  • 颜色系统偏单调：大面积 #fff 背景搭配灰色边框，视觉平面化严重
  • 排版密度过高：面板间距紧凑，长列表没有虚拟滚动，大量数据时卡顿
  • 交互反馈弱：操作（删除、保存、终止）没有确认对话框和 toast 提示
  • 数据可视化缺失：运行状态只有原始 JSON，缺少趋势图、耗时分布图等
  • 暗色模式缺失：长时间看大屏不友好
  • 筛选和排序能力不足：分析历史缺少时间范围筛选和结论置信度排序
  • Header 过于简单：缺少系统状态指示器（连接状态、最后心跳等）
